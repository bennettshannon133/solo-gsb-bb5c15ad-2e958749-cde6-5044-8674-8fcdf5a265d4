# 过敏原残留追踪（Allergen Residue Tracker）

为**共用设备的小型食品加工车间**设计的 Web 应用：按时间录入每个批次的配方过敏原、依次使用的设备以及设备清洗记录，系统逐步推演每台设备上的过敏原残留，回答两个核心问题：

1. **每个批次最终含哪些过敏原？**（配方自带 + 从共用设备交叉污染继承）
2. **每种继承到的过敏原是从哪来的？**（可逐步展开的传播来源链，逐层追溯到某个批次的配方源头）

技术栈：Node.js + Express（后端/API/推演引擎）+ 原生 HTML/CSS/JavaScript 前端（无框架、无打包步骤），JSON 文件持久化（无需数据库）。

## 一条命令启动

```bash
docker compose up --build
```

启动完成后浏览器打开：

> **http://localhost:3000**

- 端口：容器内 `3000`，映射到宿主机 `3000`（修改 `docker-compose.yml` 中 `"3000:3000"` 可改宿主机端口）。
- 依赖安装、数据目录初始化均在镜像构建/容器启动时自动完成，无需手动执行任何初始化脚本。
- 首次启动会自动写入一套**演示数据**（4 台设备、3 个批次、2 条清洗记录，便于立即看到跨污染链路）；数据保存在 Docker volume `allergen-data` 中，重启不丢失。不想预置数据时，删除 `docker-compose.yml` 里的 `SEED_DEMO` 环境变量即可。

停止：`Ctrl+C`（后台运行用 `docker compose up -d`，停止并删除容器用 `docker compose down`）。

## 本地直接运行（不用 Docker）

要求 Node.js ≥ 18。

```bash
npm install
npm start
```

同样访问 **http://localhost:3000**。数据文件默认在 `./data/db.json`（首次启动自动创建）。

可选环境变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | 监听端口 |
| `DATA_FILE` | `./data/db.json` | JSON 数据文件路径 |
| `SEED_DEMO` | 未设置 | 设为 `1` 时，启动若发现库为空则自动灌入演示数据 |

## 推演规则（模型说明）

所有「批次步骤」和「清洗记录」按时间混排成一条时间线，从头逐步模拟：

1. **批次接触设备（先继承，后留渍）**
   - 批次先把设备上**已有、而自己尚未携带**的过敏原**继承**到自身；
   - 再把自身当前携带的全部过敏原（配方过敏原 + 此前各步继承到的）**留渍**到该设备上，后续设备和批次可继续继承。
   - 同一步内刚留下的残留不会被自己重复继承。
2. **清洗只移除所选过敏原**：勾选哪些就移除设备上的哪些；未勾选的原样保留。勾选了当时设备上并不存在的过敏原时，该次清洗对该过敏原无效（界面会明确标出）。
3. **同一分钟**内既有清洗又有批次接触时，**清洗先执行**（视为接触前的换产准备）。
4. 步骤时间留空时回退使用批次时间。

页面提供：

- **残留传播时间线**：每个清洗/接触事件可展开查看事件后的设备残留快照、本步继承明细与来源；
- **各批最终过敏原**：区分「配方自带 / 交叉污染继承」，每种过敏原可逐级展开来源链
  （例：C 批在烤箱继承小麦 → 该小麦来自 B 批次从搅拌缸带来 + A 批次直接留渍 → 根源是 A 批配方）；
- **设备最终残留**：推演结束时每台设备上的残留及其来源；
- **修改即重推演**：任何记录的新增、编辑、删除（含删除设备时的级联清理）后，服务端立即基于全部记录重新推演并返回；也可点右上角「↻ 重新推演」手动刷新。

## 页面结构

- **📊 推演结果**：时间线 / 批次最终过敏原与来源链 / 设备最终残留
- **📦 批次录入**：批次名称、时间、配方过敏原（内置 9 种常见过敏原 + 可自定义）、按顺序排列的设备步骤（每步可选时间与备注，可上下调整顺序）
- **🧽 清洗记录**：设备、时间、本次移除的过敏原勾选、备注
- **⚙️ 设备管理**：设备增删改；删除设备会同步清理相关步骤与清洗记录并重新推演；可一键载入演示数据

## HTTP API

所有写操作成功后都返回完整的最新状态（`{ data, knownAllergens, trace }`），前端据此整体重渲染。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 原始记录 + 已知过敏原 + 推演结果 |
| POST/PUT/DELETE | `/api/equipment[/:id]` | 设备增改删（删除有级联） |
| POST/PUT/DELETE | `/api/batches[/:id]` | 批次增改删（含步骤） |
| POST/PUT/DELETE | `/api/cleanings[/:id]` | 清洗记录增改删 |
| POST | `/api/seed-demo` | 空库时灌入演示数据（非空返回 409） |

## 说明与边界

- 定位为小型车间单机工具：持久化采用 JSON 文件 + 原子改名写入，适合低并发的录入场景；未引入数据库与用户体系。
- 残留模型是**定性**的（有/无该过敏原及其来源），不建模残留量与清洗效率百分比；清洗对过敏原是「移除 / 不移除」的确定性结果。
